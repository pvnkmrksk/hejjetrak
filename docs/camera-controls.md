# Native camera capabilities and controls

The camera crate exposes serializable Rust values, independent of the desktop and agent frontends. `Camera::capabilities()` queries the live device; `set_control(CameraControlRequest)` validates support/range/step, performs the operation on the owning capture worker and reads the actual state back. `open_with_format(id, CameraFormatRequest)` selects an explicitly supported resolution and rate. Invalid dimensions, nonfinite values, unsupported formats and unsupported hardware controls return errors. Format changes require reopening capture and recalibrating the image geometry; frontends must keep those calibration epochs distinct.

`Camera::open(id, fps)` retains the default preference for a bounded format near 640×480. Explicit format requests use exact advertised dimensions instead of silently choosing another resolution. Automatic FPS is `null` in the shared request. Capture is bounded to 8 million pixels and 8192 per axis. The macOS adapter sets native CoreVideo output dimensions, filters transitional buffers and applies exact rational frame duration after the session configuration commits. No Rust image scaling conceals a negotiated size.

Capabilities contain the configured output dimensions/rate, bounded supported formats and frame-rate ranges, supported exposure modes, numeric exposure/gain metadata, and device-specific warnings. Numeric controls expose `value`, `minimum`, `maximum`, `step`, `unit`, `writable` and `unsupported_reason`. Missing bounds remain unknown. Read-only, inactive, disabled and automatic numeric controls cannot be set through this API. A successful setter returns readback; accepting a GUI worker command into its queue is separately an asynchronous acknowledgment.

## Platform boundaries

- **macOS / AVFoundation:** supported automatic and locked exposure modes are queried through `isExposureModeSupported:`. A camera may expose neither mode. The macOS SDK marks numerical `exposureDuration`, `ISO` and `setExposureModeCustomWithDuration:ISO:completionHandler:` unavailable on macOS; numerical exposure/ISO are consequently explicit unsupported capabilities. The API does not call unavailable selectors or emulate manual exposure in image processing. See Apple's [device exposure documentation](https://developer.apple.com/documentation/avfoundation/avcapturedevice/exposureduration) and the availability annotations in `AVCaptureDevice.h` in the installed macOS SDK.
- **Windows / Media Foundation via Nokhwa:** advertised uncompressed formats and numeric exposure/gain are exposed where the driver permits them. Exposure uses native `log2(seconds)` units; gain uses driver units. Nokhwa's current backend preserves the existing automatic/manual flag when setting a value and does not expose a flag-changing setter. Exposure mode changes therefore return an actionable unsupported error. The dependency currently omits exposure bounds on some controls; missing bounds are reported as unknown, with final validation delegated to the driver. See [Nokhwa's camera API](https://docs.rs/nokhwa/latest/nokhwa/struct.Camera.html) and [Microsoft's exposure contract](https://learn.microsoft.com/en-us/windows/win32/api/strmif/ne-strmif-cameracontrolproperty).
- **Linux / V4L2 via Nokhwa:** standard absolute exposure is preferred when exposed (`100 microseconds` per native tick); older exposure and gain controls retain driver units. Standard auto/manual exposure is available only when reported by the device. Unavailable or inactive controls remain unsupported. Nokhwa's format abstraction supports integer FPS; fractional explicit FPS requests return an error instead of rounding. See the [V4L2 camera controls](https://docs.kernel.org/userspace-api/media/v4l/ext-ctrls-camera.html).

## Local evidence

`runs/camera-controls-native/` contains metadata from the built-in FaceTime HD camera on this Mac, using the pure Rust `camera_probe` example in an ad hoc signed local app. No camera pixels were stored. The device advertises seven bounded formats with 15–30 fps ranges. Explicit 640×480/30 and 1280×720/15 were opened and delivered actual frames; status readback and errors are retained in the JSON reports. This built-in camera exposes no supported automatic/locked exposure modes through AVFoundation, so both mode requests and numerical exposure/ISO requests were rejected without interrupting frame delivery. This is evidence of honest unsupported behavior, not evidence of working manual exposure on another camera. Concurrent builds can cause dropped delivered intervals; these probes are configuration/functionality checks, not camera throughput benchmarks.

Windows strict cross-target Clippy passes; native Windows hardware behavior has not been exercised here. Linux camera cross-check remains blocked on this Mac by missing `linux/videodev2.h`; native Linux hardware behavior has not been exercised here. Camera controls never establish physical sphere-tracking accuracy.
